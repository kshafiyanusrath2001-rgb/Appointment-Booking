# Assumptions and Limitations

## Assumptions

### Timestamps: UTC only
- Every timestamp must include an explicit `Z` or `±HH:MM` offset. Timestamps
  without an offset are rejected rather than assumed to be UTC or server-local time.
- Valid timestamps are normalised to UTC instants before comparison and storage,
  and are always returned in UTC (`…Z`).
- Accepted format: `YYYY-MM-DDTHH:MM:SS[.f{1,9}](Z|±HH:MM)`. Other ISO 8601
  variants (date-only, week dates, basic format `+0530`, offsets with seconds,
  lowercase `z`) are rejected for predictability.
- Precision is nanoseconds; the smallest valid duration is 1 ns.
- Supported range after normalisation: years 0000–9999 UTC.
- Leap seconds (`:60`) are rejected, consistent with `java.time`.

### Interval convention
- Appointments are half-open intervals `[startTime, endTime)`.
- Back-to-back appointments (one ends at 10:00, the next starts at 10:00) are allowed.
- Duration must be strictly positive.

### Status semantics
- `ACTIVE`: occupies its time slot and blocks overlapping bookings for the same provider.
- `CANCELLED`: kept for history; never blocks any booking.
- The only transition is `ACTIVE → CANCELLED`. There is no un-cancel or reschedule.

### Identifiers
- `appointmentId` is generated by the server (random UUID). Clients can't choose it.
- The `Appointment` constructor also rejects blank appointment IDs and provider
  IDs, and rejects an end time that is not strictly after the start time.
- `providerId` is an opaque, case-sensitive string compared exactly (`"p1"` ≠
  `"P1"` ≠ `"p1 "`). It must be non-blank. There's no provider registry, so any
  non-blank string is accepted as a provider.
- Over HTTP, identifiers and timestamps must be JSON strings (numbers are rejected).

### Cancellation semantics
- Only an existing `ACTIVE` appointment can be cancelled.
- Cancelling an unknown ID returns "not found" (HTTP 404).
- Cancelling an already-cancelled appointment returns "already cancelled"
  (HTTP 409). It is not treated as success.

### Concurrency
- Single process, single JVM instance. All booking/cancellation state changes
  are serialised by one lock: the store instance's monitor, taken by
  `AppointmentService`. This also holds when several service instances share a store.
- Under concurrent overlapping requests for the same provider, exactly one
  succeeds and the rest receive `BOOKING_CONFLICT`. Which one wins isn't
  specified (no fairness or first-come ordering guarantee).
- A booking racing with the cancellation of the appointment it overlaps may
  either succeed or conflict, depending on which acquires the lock first. Both
  outcomes keep the invariant.

## Known limitations

- **No durability.** Data lives in memory and is lost on restart.
- **Single instance only.** The JVM lock doesn't coordinate multiple processes
  or hosts. Horizontal scaling requires moving the invariant into the database
  (see DESIGN.md §9).
- **Global lock.** Bookings for different providers are serialised. Fine at
  prototype scale; a throughput limit under heavy load.
- **Linear conflict scan.** O(n) in the number of the provider's appointments,
  including cancelled ones.
- **No request-size limit** on HTTP bodies, and no rate limiting.
- **Provider IDs are compared exactly.** `"p1"`, `"P1"` and `"p1 "` are three
  different providers. If clients aren't consistent, the same real provider
  could be double-booked under two spellings. (Review finding R1; deliberately not changed.)
- **No authentication/authorisation.** Anyone can cancel any appointment by ID,
  and conflict responses reveal the conflicting appointment's ID.
- **No business-hour, past-date or maximum-duration rules.** Booking in the
  past or for years at a time is allowed.
- **No list/search endpoint**, only fetch by ID.
- **First validation error only**: multiple invalid fields are reported one at a time.

## Risks

| Risk | Impact | Mitigation in place / future |
|---|---|---|
| A caller writes directly through the store instead of the service | The booking conflict invariant can be bypassed | The service serializes its check-and-write operation; the `Appointment` constructor and store replacement guard preserve basic record/index integrity, but direct `add`/`replace` calls do not perform conflict detection |
| Moving to a database with naive "check then insert in a transaction" | Phantom-read race → double booking | Documented: use an exclusion constraint, row lock or SERIALIZABLE |
| Clients sending local times without offset | Rejected (400) | Intentional; error message shows the expected format |
| Concurrency tests depend on timing | Could theoretically pass without the lock | `SlowAppointmentStore` widens the race window; mutation testing has not been run |

## Possible future improvements

- Database persistence with a PostgreSQL `EXCLUDE USING gist` constraint on `(provider_id, tstzrange(start, end, '[)'))` for active rows.
- Per-provider locking (or DB-level locking) to remove cross-provider contention.
- A sorted per-provider index (e.g. `TreeMap` by start time) of active appointments for O(log n) conflict checks.
- Idempotency keys on booking requests so client retries don't create duplicates.
- Request body size limits, structured logging, metrics.
